> ⛔ **這兩個檔案到目前為止，沒有任何人、在任何地方執行過一次。**
>
> Apps Script 只能在業主的 Google 帳號裡跑，repo 裡沒有、也不可能有任何方式驗證它。
> 設計上的補償是「**不在檔案裡斷言，改在業主機器上探測**」：
> 每一個不確定的 API（`Charts.ChartType['RADAR']`、`EmbeddedChart.getAs('image/png')`、
> `Body.insertTableOfContents`、舊版 Charts 服務）都是**方括號取值 ＋ 執行時探測 ＋
> try/catch ＋ 自動降級**，絕不直接呼叫；任何一層失敗最壞只會讓圖變成一張數值表，
> 不會讓報告丟例外。探測結果印在報告的**附錄C**。
>
> **業主的第一次產生報告就是這支程式的第一次測試**，要檢查什麼、要回報哪幾行，
> 全部寫在 `docs/owner-guide-多醫院多演習.md` §14.9。在拿到那份回報之前，
> 這一塊的狀態是「**已實作、未驗證**」，不要當成已交付。

與這份文件原本的設想有三處差異，記在這裡免得之後對不上：

1. **§3.1 寫「`DocumentApp` 沒有插入頁碼或自動目錄的 API」—— 頁碼那半對，目錄那半存疑。**
   頁碼確實完全沒有 API（所以範本 Doc 是**必要條件**不是便利設施）；自動目錄則改成
   `typeof body.insertTableOfContents === 'function'` 的 feature-detect，沒有就跳過
   `{{SEC_目錄}}` 並列進附錄D。
2. **§3.1 的「待驗證：Sheets 到底有沒有雷達圖」沒有被解決，是被繞過。** Sheets 的圖表
   編輯器 UI 有雷達圖（原主張「Sheets 沒有雷達圖、必須做 SVG→canvas 光柵化」是錯的），
   但那**不等於** Apps Script 的 `Charts.ChartType` 列舉有 `RADAR` 成員（Sheets REST API 的
   `BasicChartType` 就沒有）。兩邊都未經實機驗證，所以兩邊都不採信：執行時探測，
   不可用就用 COLUMN 畫同一組數值並在圖下印一行中文說明。**沒有建立任何光柵化子系統。**
   等角立體圖刻意不重現 —— 它就是 `stats.potentialByS4`，群組直條傳達完全相同的數字。
3. **§3.1 的另一條路（Drive API HTML→PDF）沒有採用。** 它繞得過頁碼限制，但產出是
   「一份 PDF」而不是「一份業主可以自己改版面、自己補結論的 Google 文件」，
   而 §3.2 大綱裡有五章（參演規模、評核委員名單、與前次比較、改善行動、結論建議）
   **永遠只能由業主自己補**。可編輯的 Doc 是方案 B 的產出規格，不是副產品。

報告的統計數字**一律原樣取自 `action=analysis`，絕不另算**（否則儀表板與紙本會互相打架，
而業主沒有任何辦法判斷哪一個才對）。唯一的例外是 ICC(2,k) 的本機驗算：`stats.icc2k` 是一個
裸數字，而且只要有一題只被一位評核官評過整個資料集就變 `null`（§4.4），所以報告必須能
**具名說出是哪幾題**造成的，不然封面印一個「—」沒人知道為什麼。

同時新增一張「**報告快照**」工作表（只追加、永不覆寫），把當下解析出的
階段／情境／指標／潛能／4S 與各題平均寫死 —— 這直接補掉 D3，也是未來「與前次演習比較」
唯一可能的資料來源。它**永遠不寫入任何人員代號、逐評核官分數、觀察紀錄原文，沒有開關**：
commit `54b33dd` 拿掉 `#detail` 是刻意的決定，方案 B 不得成為繞過它的後門（§4.1）。
後端從不讀「報告快照」與「_報告暫存」，所以這兩個新分頁對評核單與分析端零影響。

- **統計程式碼一行都不用改**。每場有自己的紀錄檔 → `:263` 全表讀取和 `:276-285` 單鍵去重
  **剛好變成正確的**；CLAUDE.md 記錄的 `icc2k=0.6858` / `within1=0.9846` 自動保持有效
- **一輩子只重新部署一次**。之後加醫院、加演習、換金鑰全是改試算表
- **不動 `演習資訊` 的 key/value 形狀**（`:485-499`）→ `README.md:23-122` 這份業主實際在填的
  對外契約**逐字保持有效**

**新增一家醫院** = 註冊表加一列（新 `醫院代號`）＋ 複製兩個範本檔。
**同院第二場演習** = 加一列，`醫院代號` 沿用、`演習代號` 換新。

同院兩場的分離點逐一確認：

| 面向 | 今天 | 方案 A |
|---|---|---|
| 分數 | 同一紀錄檔，同題號互相覆蓋（D1） | 不同紀錄檔，`1-1` 永不相遇 |
| 評分標準 | 一份試算表只有一套（`readCriteria_:513`） | 各場自己的 `評分標準` → **桌面推演與實兵演練可用不同尺度**（今天做不到） |
| 題庫與指標 | 只能整張覆蓋，覆蓋瞬間觸發 D3 | 各自獨立，互不干涉 |
| 人員代號 | 一份名單 | 各自名單，不會誤選到另一場的代號 |
| 手機進度 | D2 碰撞 | `exerciseEvalDone:wanfang-7f3a2c/2026b:A1` |
| 在飛行中的送出 | D5 | 「準備下一場」是加一列而非改現有設定表 → 陷阱基本消失 |

**次要選項**：若醫院堅持兩場共用一份紀錄檔，把 `紀錄分頁名稱` 填成不同分頁
（`評核紀錄_創傷` / `評核紀錄_大量傷患`）即可，`t.recordSheet` 已經是每列的值。
但 `(紀錄試算表ID + 分頁名稱)` 必須唯一，`assertRegistrySane_` 會硬擋。

**權限注意**：Web App 必須用「執行身分：我」（評核官是匿名的，改成「存取使用者」會要求每支手機
登入 Google 並授權），所以本室腳本帳號必須對該院設定檔有「檢視者」、紀錄檔有「編輯者」
（`setNumberFormat:190` 與 `setValues:192` 都是寫入）。兩種擁有權模式註冊表都支援：
(A) 本室 Drive 擁有、分享給醫院品管 —— `openById` 必定成功，但分數存在第三方 Drive；
(B) 醫院自己擁有、分享給本室腳本帳號 —— 歸屬乾淨，但該院 Workspace 管理員關閉對外共用就全失敗。
→ 這一題直接連到 §5 的第 1 題。

### 2.2 兩個更便宜的替代（醫院數少時優先）

完整性批判找出來、沒人當成主方案評估的選項：

1. **改 `RECORD_SHEET_NAME` 而不是 `RECORD_SPREADSHEET_ID`** —— 一場演習一個**分頁**，同一份紀錄檔。
   那個變數只在 `:134` 和 `:261` 兩處用到，**約 5 行改動**，不插欄、不 fill-down，
   業主的動作是「分頁右鍵 → 複製 → 改名」。設定表同理用分頁後綴（`項目與問題_2026A`）
   —— 而且順便解決 D3：去年的分頁還在，舊的 join 目標還讀得到。
2. **零程式碼版**：每場演習前，業主對紀錄檔「檔案 → 建立副本」、改名加日期，再把正本資料列刪掉。
   這**一個 Drive 動作**就擋掉 D1。不需程式、不需部署、不需工程師。

> 醫院數 ≤ 2、一年一場 → 方案 A 是過度建設，走 (1)。

### 2.3 被否決的方案，理由

**B（單一部署＋場次代號分欄）** — 分析價值最好（複合鍵 `runId+'␟'+問題ID`、`action=trend`、
跨院彙總都在同一張表上），但隔離只有 4 分，**而且它自己承認矛盾**：

> 「設定試算表必須由業主獨佔編輯。絕對不能把編輯權開給個別醫院，否則該院看得到也改得到其他每一家的設定。」

但整件事的前提就是醫院品管中心自己手改試算表。要嘛 A 院拿到含 B 院題庫／代號名冊／分數的
檔案編輯權（這是透過 Drive 分享做出的跨租戶讀寫授權，完全在程式之外），
要嘛沒人能編輯、自助化的好處歸零。遷移成本也最大（四張手改試算表各插一欄＋全表 fill-down，
一格漏掉 → 題目從選單消失，或更糟：該列同時掉出 `analysisRows`/`coverageRows`/`learningRows`
三個陣列（`:308-313`），從所有圖表消失且無錯誤）。另外設定分支無金鑰，
`?run=<別院的runId>` 就能拿到該院完整題庫與代號名冊。

**C（Kit 模式）** — 隔離最強（Google 檔案邊界，不靠我們的程式碼；`selfcheck` 的
`recordRows==0` 硬性驗收是全套設計裡最好的驗證閘門），但**每加一場演習都要工程師做一次
Web App 部署**，結構上業主就不可能自助（它自己承認「業主其實還是不能自助完成全程」）。
後端改一次 = N 次手動重新部署，踩在「選錯 New deployment 會悄悄換掉 `/exec`」的陷阱上。
10 家 × 2 場 × 3 年 ≈ 120 份試算表 + 20 個腳本專案，同時有設定漂移與程式漂移。
另外它的前提需要把**獨立腳本**改成**容器綁定範本**，而現有程式從不呼叫 `getActiveSpreadsheet`
（已驗證），這本身就是一次不小的遷移。

**D（Postgres）** — 資料模型最乾淨、趨勢分析最強（`(tenant_id, exercise_id, question_id, evaluator_code)`
是 DB 強制的自然鍵，append-only + `v_latest_scores` 保留稽核軌跡，寫入時快照標籤直接解決 D3），
但為了一個「每場各自一個檔案就零程式碼解決」的碰撞問題引入第二套 runtime。
免費方案**閒置 7 天會自動暫停** —— 對一季一次的演習，等於演習當天第一位評核官
送出重試 3 次後失敗，而業主無法診斷也無法修。免費方案無 PITR，一次誤刪不可恢復
（Sheets 有逐格修訂記錄和 Ctrl+Z）。而且業主永遠失去「打開紀錄表看一眼」這個他唯一會用的除錯工具。
它也從未回填現有 `評核紀錄` 的列 → 歷史分裂在兩套儲存。

### 3.1 建議路線：A 先上，B 當正式交付物

**第一週可上的 A** — `Analysis.html` 目前**完全沒有任何列印樣式**，而 `.panel{display:none}`
讓五個分頁只有一個會印出來；`.chartbox svg{height:100%}`、sticky `th`、`.table-wrap{overflow:auto}`
也都會壞。加一個「報告預覽」模式：封面在最上、五個分頁展開成連續章節、`@media print` 分頁控制、
螢幕上顯示列印設定提示卡 ＋ 兩個勾選（匿名模式、是否附逐題明細）、封面「報告版本」欄位
可直接打字（`contenteditable`，不存檔）。一個檔案、不用部署、不用授權，圖表在 PDF 裡還是向量。

**硬天花板要先講清楚**：Chrome 不支援 CSS 分頁邊界（`@page{@bottom-center{content:counter(page)}}`），
**頁碼只能靠瀏覽器的列印頁尾**，而那個頁尾會印出儀表板網址 —— 也就是把存取控制印在報告上。
業主得在「有頁碼」和「不洩漏網址」之間選一個。一份 20 頁、沒頁碼沒目錄沒文件編號的 PDF，
不是可歸檔的醫院品質記錄。**→ A 是很好的內部檢視版，不是交付物。**
另外「背景圖形」勾選框沒勾的話，iso3D 與 HSL 色譜會印成全白。

**正式交付走 B** — 在設定試算表上掛容器綁定腳本 → 自訂選單「產生演習評核報告」→
讀 `action=analysis` → 組進一份**範本 Google 文件** → 匯出 PDF。關鍵四點：

1. 容器綁定腳本**不需要部署**（存檔重載即生效）→ Phase 1 對 `ConfigWithSubmit.gs` 改 0 行、
   重新部署 0 次 —— 繞開業主唯一拉不動的那根槓桿
2. **頁碼、院徽、字型、簽核欄放在範本 Doc 裡**由業主自己用 Google 文件改
   （`DocumentApp` 沒有插入頁碼或自動目錄的 API，所以這不是偷懶而是唯一解）。
   未來九成的「版面再美一點」不需要工程師
3. 檔案落在**業主自己的雲端硬碟**（執行身分是「打開試算表的人」，不是 Web App 的 execute-as-Me）
4. 產出是**可編輯的 Doc** → 摘要／結論／改善建議這些資料永遠生不出來的章節，業主自己補

同時產一張「報告快照」分頁，把當下解析出的 階段/情境/指標/潛能/4S **寫死** → 直接補掉 D3。

**產出時間約 30–90 秒**（二十幾次 `appendImage`/`appendTable` 加 PDF 匯出），
對話框一定要有進度狀態，否則業主會連按兩次產生出 v2。

**待驗證**：有 agent 主張「Sheets 沒有雷達圖，所以必須做 SVG→canvas 光柵化子系統」。
等角立體圖的部分正確，但**Google Sheets 的圖表編輯器確實有雷達圖和量規圖**。
動工前先在 Sheets UI 確認 —— 如果有，6 張圖裡有 4 張不需要光柵化，
Phase 1.5（整個設計裡最依賴瀏覽器、風險最高的部分）可以直接砍掉，只有 `svgIso3D` 需要特殊處理。

**另一條沒人考慮的路**：用 Drive API 的 HTML→PDF 轉換（`Drive.Files.insert` 帶 `text/html` body
＋ `convert=true`）而不是 `DocumentApp`。這同時繞過 `DocumentApp` 的頁碼限制**和**
SVG 光柵化機制，現有的 inline SVG 可以直接當 HTML/CSS 嵌入。

### 3.3 ⚠️ 最大的問題不是工具，是資料缺口

**系統目前沒有任何自由文字欄位。** POST payload 只送 `{id, score}`（`Start.dc.html:305`），
前端、payload、`評核紀錄` 三層都沒有地方放質性觀察。
而 `Analysis.html:33` 統計方法頁自己寫著「建議保留每位評核官原始評分與觀察紀錄」—— 系統並沒有保留。

> **不管選哪個報告方案，產出的都會是「統計完整、敘事空白」的文件。**
> 只有「回應 3.4」沒有「為什麼」，品質委員會無法形成改善依據。

| 缺口 | 需要什麼 | 影響 |
|---|---|---|
| **每題觀察紀錄**（最關鍵） | 問卷加選填意見框、payload 加 `comment`、`評核紀錄` 加「觀察紀錄」欄 | 報告沒有任何質性內容 |
| 低分理由必填 | 評 1–2 分時強制說明 | 「最弱的三項」永遠無法自我解釋 |
| **「未觸發」vs「表現差」混在一起** | 至少單獨列「未觸發率（1 分占比）」— **純新算法，不需新資料**。要區分「劇本沒走到」vs「評核官沒看到」才需要新增 N.A. 旗標 | 1 分的定義是「劇本未走到此條件」，卻和 2–5 分一起平均。平均 3.0 可能是「表現普通」也可能是「一半評核官根本沒看到」 |
| 改善行動計畫 | 新增一張業主手填的「改善行動」工作表，報告只負責印出 | 品質委員會最重要的一張表（PDCA 閉環），目前完全沒有 |
| 評核委員名單 | `人員代號` 目前是無任何欄位的平面清單（`readCodes_:501-511`，`value===label`），無姓名、職稱、單位、院內外別 | 報告列不出委員名單；也無法分組看院外委員是否系統性打得較嚴 |
| 應評配置表（誰該評哪個情境） | 新資料 | `評核官人數` 是「實際出現過的代號聯集」（`:347-348`）→「每個情境是否都有足夠人數評核」算不出來，缺漏是隱形的 |
| 情境層級時間資訊 | 通報／到院／檢傷完成時間戳 | `送出時間` 有寫入（`:178`）但 `buildAnalysis_` 根本沒去讀；且是「送出」時間不是「事件發生」時間 → 沒有反應時間 KPI、沒有時序圖 |
| 演習腳本時間軸（inject 預定 vs 實際） | 全新 | 實兵演練報告的核心圖表之一 |
| 參演規模分母（單位／人數／模擬傷患數／收治數） | `演習資訊` 只有六個 key/value 列，沒有位置放 | 醫院報告第一節通常要寫 |
| 題目權重與關鍵題標記 | `對應指標` 加「權重」／「關鍵指標」欄 | 所有題目等權平均，算不出加權總分，也無法標示「關鍵題未達標」 |
| 合格標準／目標值 | 門檻欄位 | 只能說平均分，不能說達標／未達標。目前 3.3/4.0 門檻寫死在 `Analysis.html:46` 的 `cls()` 裡，業主改不到 |
| 現場照片 | Drive 資料夾慣例 | 醫院報告通常要附 |
| 簽核與文件管制（製表／審核／核定／會議日期／文件編號／版次） | 範本 Doc 手填，或 `演習資訊` 增列 | — |
| **不需新資料、只是目前沒人算** | 缺漏清單（`readItems_` 全部問題ID 減去實際有分數的）、評核官寬嚴傾向、SD 過大題目清單 | — |

> **建議：把「觀察紀錄」欄和「演習代號」綁進那一次不可避免的重新部署裡，
> 而不是把部署風險花在一顆報告按鈕上。**
